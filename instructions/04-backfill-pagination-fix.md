# 04 - backfill_ap_events ページネーション修正（search_afterカーソル方式）

## 推奨モデル: Sonnet

理由: 03の調査で原因（`page`パラメータが機能しない）と修正方針（`search_after`カーソル方式）が
確定済み。実測で動作確認済みのアプローチに沿って実装するだけの機械的なタスクのため。

---

03の調査で判明した `backfill_ap_events()` のページネーションバグを修正してください。
execute all commands automatically without stopping.

## 背景

Mist の `devices/events/search` API は `page` パラメータをサポートしておらず、`page=2,3,...` を
付けても常に同じ1ページ目（最新100件）が返る。現在の実装は取得件数が`total`に達するまでループする
条件になっているため、同じ100件を何度も取得し続け、その2回目以降が全て「重複」としてカウントされて
いた。

より深刻な問題として、`CONNECTIVITY_TEST`のような頻出イベントが100件枠を埋め尽くすため、
実質1〜2日分程度しか遡れておらず、それより古い再起動・DFSイベントに到達できていなかった
（例: 1_Kyobashiは7日で453件あるうち、実際には1.37日分しか取得できていなかった）。

APIレスポンスには正しいページング手段（`next`フィールドの`search_after`カーソル、または
`end`パラメータに最古のtimestampを指定する方式）が含まれており、実測で動作確認済み。

## 【1】バックエンド: `mist/client.py` のページネーション修正

`get_site_device_events()`（`backend/mist/client.py:251-261`付近）を以下の方針で修正:

- `page`パラメータによるループを廃止
- レスポンスの`next`フィールド（`search_after`カーソルを含むURL）を辿る方式に変更
  - または、取得したイベントの中で最も古い`timestamp`を`end`パラメータに指定して再リクエストする方式でもよい
    （どちらか実装しやすい方でよいが、`next`フィールドが提供されているならそちらを優先）
- ループの停止条件を以下に変更:
  - 返却イベント件数が0件になったら停止
  - 前回リクエストと同一のカーソル（または同一の`end`値）が返ってきたら停止（無限ループ防止）
  - 加えて安全弁として、最大ループ回数（例: 50回）に達したら強制停止し、警告ログを出す
- 取得したイベントは`timestamp`で重複除去してから返す（同一イベントを2回カウントしないため）

## 【2】バックエンド: カウント表示の文言修正

`scheduler.py` の `backfill_ap_events()` のレスポンス・ログで、`duplicate_events` に相当する概念は
修正後は「DB上の既存レコードと衝突してスキップされた件数」という正しい意味になる。ただし紛らわしいため、
以下の文言に統一する:

- `duplicate_events` → `skipped_existing`（フィールド名も変更可、フロント側と合わせて調整）
- フロントエンドのトースト文言: 「重複N件はスキップ」→「既存N件はスキップ」

## 【3】フロントエンド: `history/page.tsx` の文言修正

バックフィル完了トーストの文言を上記に合わせて更新:

```
例: 「67件の新規イベントを取得しました（既存213件はスキップ）」
```
